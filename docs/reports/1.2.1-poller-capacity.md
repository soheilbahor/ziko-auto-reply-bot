# ZIKO 1.2.1 — Child-bot poller capacity hotfix

## Scope

This hotfix addresses the reviewed failure mode in which enabled child bots could
remain blocked behind the polling semaphore while `/tenants` showed only the
database `enabled` flag.

## Changes

- Raised the default `ZIKO_TENANT_MAX_CONCURRENT_POLLERS` from 10 to 50, matching
  the default global tenant registration cap.
- Kept the limit configurable with the environment variable.
- Added explicit in-memory running and waiting sets to `TenantBotManager`.
- Added queue-entry and slot-acquisition log messages; log messages include IDs
  and counts, never bot tokens.
- Added `runtime_status()`, `waiting_count()`, and corrected `running_count()`
  to report actual semaphore occupancy rather than supervisor task count.
- Updated the platform `/tenants` command to show enabled state separately from
  polling runtime state and to show active/waiting totals.
- Added regression tests for queue visibility and the default concurrency limit.

## Validation

- `python -m compileall`: passed.
- `bash -n` for all shell scripts: passed.
- Focused `pytest tests/test_tenant_bots.py`: could not collect because `aiogram`
  is not installed in the offline environment.
- No live Telegram polling or Ubuntu VM test was performed.

## Operational note

If an operator deliberately configures a concurrency limit below the number of
enabled tenants, excess bots remain queued while all slots are occupied. The
`/tenants` command and logs now make this visible. The default of 50 allows all
50 default-capacity tenants to poll concurrently; deployments should size this
limit for available memory, file descriptors, CPU, and Telegram/API workload.
