## Phase 2 (update, backup and rollback) — verification

Updater scenarios were run with the real `scripts/update.sh`, a file-based release server,
a v1 database with data, a child database and a registry. The sandbox has no systemd, so
`systemctl`, `runuser` and `gh` were test-only fakes, and the venv used a no-op `pip` and a
stdlib `sqlite3`-backed `aiosqlite` stand-in. Those fakes are NOT part of the release.

| Scenario | Result |
|---|---|
| A: 1.4.0 → 1.4.1, startup migrates the DB | Pass. Schema 1→2; custom status text, Business connection, delivery history and child DB rows preserved; `.env` untouched; no plaintext snapshot left; installed tree equals the verified release; health check PASSED |
| B: activation fails after the new release starts | Pass. Automatic rollback: VERSION 1.4.0, code equal to the original, DB back to schema 1 with all data, child data intact, service restarted |
| C: migration cannot run on the live data (dry-run) | Pass. Stops at `DATABASE_MIGRATION`; live DB still schema 1; code still 1.4.0; service restarted |
| Platform backup → restore with manifest | Pass (regression test) |
| Manifest: tampered, unlisted, missing | Pass (4 unit tests) |
| Migration 1→2 on a realistic v1 database with data | Pass |

Not verified here: real systemd unit start/stop, real Telegram `getMe`, real Business traffic,
and the GitHub attestation (the sandbox `gh` is a fake). Run one update on a staging server
before production.
